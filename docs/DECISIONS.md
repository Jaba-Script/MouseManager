# DECISIONS — Mouse Manager

Формат: Architecture Decision Record (ADR). Каждая запись — «почему так», а не «что делать».
Статусы: **Accepted** (действует), **Open** (ждёт эксперимента или решения), **Superseded**.

---

## D-001 — Kotlin + Compose, один модуль, `minSdk 29`

**Статус:** Accepted

**Контекст.** Нужен небольшой инструмент под конкретный планшет. Android Studio нет,
сборка только wrapper'ом. Лишние слои (Hilt, Room, navigation-compose) увеличат время
сборки и площадь ошибок.

**Решение.** Один модуль `:app`. Kotlin 2.3.21, Compose BOM 2026.06.01, AGP 8.13.2,
`compileSdk 36`, `targetSdk 35`, Java/Kotlin 17. `minSdk 29`.
`applicationId = com.mousemanager` (подтверждено 2026-11-11).

**Почему именно `minSdk 29`.**

- `InputDevice.getDescriptor()` появился в **API 29**. Это единственный стабильный ключ
  экземпляра устройства: он переживает переподключение (проверено: `deviceId` менялся
  29 → 30 → 31, `descriptor` — нет).
- `deviceId` для привязки не годится: меняется при каждом переподключении.
- `name` + `vendorId` + `productId` идентифицируют **модель**, а не экземпляр. Две
  одинаковые мыши неразличимы; кроме того, `name` зависит от прошивки/локали.
- Без `descriptor` пришлось бы строить эвристику («имя + порт + время подключения»),
  которая ошибается именно в опасную сторону — может совпасть с клавиатурой.

**Что теряем на API 26–28.**

| Возможность | API 26–28 |
|---|---|
| Стабильная идентификация экземпляра мыши | Нет; только `name`/vendor/product, две одинаковые мыши неразличимы |
| `GLOBAL_ACTION_LOCK_SCREEN` / `SCREENSHOT` | Недоступны (появились в API 28; на 26–27 их нет) |
| `GLOBAL_ACTION_TAKE_SCREENSHOT` | Недоступно (API 34+) |
| Современные API `InputManager` | Часть есть, но без `descriptor` ключевая функция деградирует |
| Тестовая база | Нет ни одного устройства на 26–28; проверять негде |

Механизм фильтра клавиш сам по себе доступен и на 26–28, но безопасность привязки к
устройству без `descriptor` не гарантируется. Поддержка 26–28 потребовала бы отдельного
fallback-интерфейса и предупреждения «одинаковые устройства неразличимы».

**Если поддержка 26–28 всё же понадобится.** Ввести `DeviceIdentity` с двумя
реализациями: `DescriptorIdentity` (API 29+) и `LegacyIdentity` (`name + vendorId +
productId`, с явным предупреждением). Это отдельная задача, не v1.

**Следствия.** Нет поддержки Android 8–9. Нет DI-фреймворка: зависимости собираются
вручную в `MouseManagerApp`. Навигация — простое состояние экрана, без библиотеки.

## D-002 — Перехват через `AccessibilityService` + фильтр клавиш, без root

**Статус:** Accepted

**Контекст.** Нужно глобально перехватывать боковые кнопки мыши. Root нет. Обычное
приложение не видит события других устройств.

**Решение.** `AccessibilityService` с `canRequestFilterKeyEvents="true"` и
`FLAG_REQUEST_FILTER_KEY_EVENTS`. В `onKeyEvent` возвращаем `true` только для событий,
которые решили поглотить. Никакого root, никакого Shizuku, никаких `INJECT_EVENTS`.

**Проверено.** HyperOS 3 применяет флаг: `onServiceConnected flags=0x20`. События реально
приходят и гасятся (S2, 12 × `CONSUMED`).

**Следствия.** Пользователь обязан вручную включить службу в настройках. Приложение не
может включить её само. `onKeyEvent` не видит `adb shell input` (инъекция не является
аппаратным событием) — автотесты только ручные.

## D-003 — Идентификация мыши только по `InputDevice.descriptor`

**Статус:** Accepted

**Контекст.** `deviceId` меняется при каждом переподключении. За одну сессию S2 мышь
получила 29 → 30 → 31 при неизменном `descriptor`.

**Решение.** Ключ устройства — `descriptor` (стабильная строка, например
`ce5035b0…3992`). `deviceId` используется только для
диагностики и логов.

**Следствия.** Две одинаковые мыши одной модели имеют одинаковый `descriptor` и
неразличимы. UI обязан предупреждать об этом. `descriptor` может быть `null` — такое
событие всегда пропускается.

## D-004 — Перехват строго в пределах выбранных устройств

**Статус:** Accepted

**Контекст.** Служба видит клавиши **всех** устройств: клавиатуры, кнопок громкости,
пульта. Ошибка в проверке устройства заблокирует ввод.

**Решение.** Первая проверка в горячем пути — `descriptor` события входит в
`RuntimeConfig.targets`. Нет — `return false` немедленно. Список целей пуст — `return
false`. `descriptor == null` — `return false`.

**Следствия.** Клавиатура и кнопки громкости не затрагиваются, даже если их клавиши
совпадают с клавишами аккорда. Проверено в S2: `gpio-keys` и `pmic_resin` →
`PASSED_OTHER_DEVICE` (имя из S2; в продукте — `PASSED_FOREIGN_DEVICE`, D-017),
громкость работает.

## D-005 — Поглощаем только клавишу-триггер, модификаторы не трогаем

**Статус:** Accepted (политика продукта)

**Контекст.** Боковая кнопка приходит как `Ctrl↓ C↓ Ctrl↑ C↑`. Чтобы приложение не
выполнило copy/paste, достаточно не отдать ему **букву**. `Ctrl` — только модификатор,
он не производит действие сам по себе. S2 гасил все четыре события и это работало, но
продукт должен минимизировать зону поражения.

**Решение.** Поглощаем **только** клавишу-триггер (`KEYCODE_C` / `KEYCODE_V`) — её DOWN и
парный UP. `Ctrl` (LEFT/RIGHT), `Shift`, `Alt`, `Meta` **всегда пропускаются**.
Модификаторы отслеживаются (для сопоставления аккорда), но не гасятся.

### Почему не поглощать Ctrl

1. **Риск залипшего модификатора.** Если поглотить `Ctrl↓`, но по любой причине не
   поглотить `Ctrl↑` (исключение, выключение службы, смена конфига, потеря события),
   система останется с нажатым Ctrl. Это худший из возможных багов: перестают работать
   жесты, выделение и часть интерфейса, и пользователь не понимает почему.
2. **Нам не нужно его поглощать.** Copy/paste запускает буква, а не модификатор.
3. **Симметрия.** Пропуская и DOWN, и UP, мы гарантируем, что система видит полную пару
   «нажали — отпустили». Даже если наше приложение умрёт между событиями, `Ctrl↑` дойдёт
   до системы сам.
4. **Меньше поверхности.** Мы не трогаем состояние модификаторов, которое использует
   ввод в других приложениях.

### Что увидит приложение

«Голое» нажатие Ctrl без буквы: `Ctrl↓ … Ctrl↑`. По ожиданиям это инертно: символ не
вводится, стандартного действия нет. Некоторые приложения могут показать подсказку
горячих клавиш при удержании Ctrl — это косметический эффект, а не поломка. **Это
непроверенное условие:** проверяется в M2 на живой мыши. Если эффект окажется заметным,
переключаемся на атомарное поглощение всего аккорда (S2 это доказал).

### Почему поглощать и UP триггера

Если поглотить только `C↓`, приложение получит «сиротский» `C↑` — клавишу, которую оно
не видело нажатой. Обычно это безвредно, но некоторые приложения и IME могут реагировать
на release. Поглощение пары DOWN+UP убирает этот класс неопределённости.

### Неполные последовательности и потеря фокуса

| Сценарий | Поведение |
|---|---|
| `Ctrl↓` без `C↓` | Ctrl пропущен, действия нет |
| `C↓` без `Ctrl` | Маппинга нет → pass, буква уходит как обычно |
| `C↓` поглощён, `C↑` потерян | Приложение не видело DOWN, «залипания» нет; pending истекает через 1500 мс |
| `C↑` без `C↓` | Pending нет → pass (сиротский UP, безвреден) |
| `Ctrl↑` без `Ctrl↓` | Pass (сиротский UP модификатора, безвреден) |
| Два аккорда почти одновременно | Pending хранится **по keyCode** на устройство (несколько записей), оба UP гасятся |
| Служба умерла между `C↓` и `C↑` | `C↓` уже поглощён, действие не выполнено; `C↑` уйдёт в приложение как сиротский. Вреда нет; при следующем старте `armed=false` (D-006) |
| Перехват выключили между `C↓` и `C↑` | Pending UP всё равно поглощается: трекер проверяется **до** проверки `armed` (см. §6 архитектуры) |
| Устройство убрали из целей между `C↓` и `C↑` | То же: pending UP гасится, чтобы не оставить половину аккорда |
| Потеря фокуса окна | `onKeyEvent` глобальный, фокус не влияет. Действие выполняется на DOWN; смена окна за ~100 мс теоретически возможна, но практически исключена |
| Прошивка мыши не прислала `Ctrl↑` | Это сбой железа, не нашего кода: система может остаться с Ctrl. Мы не можем синтезировать `Ctrl↑` без root/Shizuku. Лечится нажатием/отпусканием Ctrl на клавиатуре или переподключением мыши; в диагностике фиксируется |

### Модификаторы и многомодификаторные аккорды

Если пользователь создаст маппинг `Ctrl+Shift+C`, поглощаем только `C`, а `Ctrl` и
`Shift` проходят. Приложение увидит «голое» нажатие обоих модификаторов. Логика та же:
модификаторы не трогаем, триггер гасим.

### Отличие от S2 и запасной вариант

S2 проверял **API**, а не политику: он гасил весь набор `{CtrlLeft, CtrlRight, C, V}`.
Продукт проверяет более узкую политику. Если на устройстве обнаружится побочный эффект
от «голого» Ctrl, переключаемся на атомарное поглощение всего аккорда: `ChordTracker`
уже знает модификаторы и триггер, изменение локальное и не затрагивает UI/хранение.

**Следствия.** Нужен трекер с несколькими pending UP на устройство. Pending UP
проверяется раньше `armed`, чтобы выключение перехвата не оставляло половину аккорда.
Repeat'ы триггера поглощаются без повторного действия.

## D-006 — Мастер-переключатель всегда выключается при старте

**Статус:** Accepted (подтверждено пользователем 2026-11-11)

**Контекст.** Если `armed` не сохранять (как в S2), после каждого убийства процесса
перехват выключается и пользователь должен включать заново. Если сохранять без защиты,
после падения приложение может молча продолжить гасить клавиши. Пользователь выбрал
безопасность: **всегда выключать**.

**Решение.**

1. `armed` **не хранится** в DataStore. Это runtime-флаг процесса.
2. При старте процесса и при каждом `onServiceConnected` — `armed=false`.
3. Включение — только явным действием пользователя в UI в текущей сессии.
4. Выключение — мгновенно: `engine.setArmed(false)`; если UI открыт, также
   обновляется состояние.
5. `targets`, профили и маппинги сохраняются как обычно — они не опасны сами по себе.

**Почему это уже crash-safe.** Флаг живёт только в памяти. Любое завершение процесса
(падение, kill системой, reboot) уничтожает его. Служба, перезапущенная системой,
поднимается с `armed=false`. Отдельный crash-guard не нужен: безопасное состояние —
значение по умолчанию.

**Поведение по сценариям.**

| Сценарий | `armed` после |
|---|---|
| Падение приложения (uncaught exception) | `false` — процесс умер |
| Система убила процесс | `false` — новый процесс |
| Перезагрузка планшета | `false` — новый процесс |
| Служба переподключилась (`onServiceConnected`) | `false` — сбрасываем явно |
| Пользователь выключил/включил службу в настройках | `false` при новом подключении |
| Activity пересоздана (поворот и т.п.) | Не меняется: процесс и флаг живы |
| DataStore недоступен | `false` — fail-safe конфиг |

**Следствия.** После каждого перезапуска приложения/планшета перехват нужно включать
вручную. Это осознанный компромисс: удобство ниже, но «забытый» перехват невозможен.
UI обязан ясно показывать «перехват выключен» и не выглядеть так, будто он работает.

## D-007 — Хранение: DataStore Preferences + `org.json`

**Статус:** Accepted

**Контекст.** Нужны настройки, профили, привязки к приложениям. Хочется минимум
зависимостей и предсказуемую миграцию.

**Решение.** `androidx.datastore:datastore-preferences:1.3.0` (проверено:
`minCompileSdk=34`, `minAGP=8.1.1`). Сложные структуры (профили, маппинги, имена
устройств, привязки) — JSON-строки, сериализация через встроенный `org.json`. Без
kotlinx.serialization и без Room.

Один экземпляр `DataStore<Preferences>` на процесс (делегат `preferencesDataStore` в
`MouseManagerApp`). Все записи — через `SettingsRepository`, никаких прямых `edit` из UI.

**Схема (ключи):**

| Ключ | Тип | Смысл |
|---|---|---|
| `schema_version` | Int | Версия схемы, сейчас `1` |
| `targets` | Set\<String\> | `descriptor` выбранных устройств |
| `device_names` | String (JSON) | `{descriptor: name}` для UI |
| `profiles` | String (JSON) | массив профилей |
| `active_profile_id` | String | активный профиль |
| `default_profile_id` | String | fallback-профиль |
| `app_bindings` | String (JSON) | `{package: profileId}` (M3) |
| `diagnostics_enabled` | Bool | подробный журнал |

`armed` **не хранится** (D-006): это runtime-флаг процесса.

**Пример профиля:**

```json
{
  "id": "default",
  "name": "Основной",
  "mappings": [
    {
      "device": "a1b2c3d4e5f60718293a4b5c6d7e8f9012345678",
      "chord": { "mods": ["CTRL"], "key": 31 },
      "action": "BACK",
      "enabled": true
    }
  ]
}
```

`device: null` = любое целевое устройство. `key` — `KeyEvent.keyCode` (`C` = 31).
`mods` — битовая маска `CTRL/SHIFT/ALT/META`.

**Миграция.** При старте читается `schema_version`. Неизвестная более новая версия →
режим «только чтение» + сообщение, перехват выключен. Старые версии мигрируются
функцией `migrate(from, to)`.

**Следствия.** JSON парсится не на главном потоке. Ошибка парсинга = fail-safe (D-018).

## D-008 — Горячий путь читает неизменяемый `RuntimeConfig`

**Статус:** Accepted

**Контекст.** `onKeyEvent` вызывается на главном потоке для каждого аппаратного события.
Чтение DataStore, JSON-парсинг или блокировки здесь недопустимы.

**Решение.** Сервис держит `@Volatile var config: RuntimeConfig`. Отдельная корутина
собирает DataStore, строит **неизменяемый** снимок (все карты предвычислены) и
публикует его одной ссылкой. `onKeyEvent` делает только чтение ссылки и O(1)-поиск.

`RuntimeConfig` содержит: `generation`, `targets`, `profiles` (готовые
`Map<ChordKey, ActionCode>`), `activeProfileId`, `defaultProfileId`, `appBindings`.
`armed` в него **не входит**: это отдельный `@Volatile`-флаг в `RemapEngine` (D-006).

**Следствия.** Смена настроек применяется с задержкой в несколько миллисекунд (запись в
DataStore + эмиссия). `armed` не зависит от перестройки снимка: включение/выключение —
мгновенное присваивание `engine.armed`, старт/подключение службы — `false`.

## D-009 — Обычные кнопки мыши не переназначаются в v1

**Статус:** Accepted

**Контекст.** Левая/правая/средняя кнопки приходят как `ACTION_BUTTON_PRESS/RELEASE`
(`BUTTON_PRIMARY` / `SECONDARY` / `TERTIARY`), а не как клавиши. Их можно увидеть только
в `onMotionEvent` после `setMotionEventSources()`.

**Решение.** В v1 обычные кнопки не трогаем. `setMotionEventSources()` не вызывается
вообще, `onMotionEvent` не переопределяется. Курсор, выделение, контекстное меню и
средняя кнопка работают штатно.

**Причина.** `onMotionEvent` + `setMotionEventSources()` **забирает** события у системы.
Режима «посмотреть и передать дальше» нет. Если забрать движение, курсор замрёт; если
забрать только кнопки — неясно, как вернуть их системе без `INJECT_EVENTS`. См. D-012.

**Следствия.** В UI — явная пометка «левая/правая/средняя не переназначаются». Будущий
ремап средней кнопки — отдельный spike с инъекцией (root/Shizuku), не в v1.

## D-010 — Набор действий v1: восемь глобальных действий

**Статус:** Accepted (подтверждено пользователем 2026-11-11)

**Контекст.** Приложение не может синтезировать произвольные клавиши: `INJECT_EVENTS` —
signature-разрешение. `startActivity` из фона ограничен. Нужен честный, проверяемый набор.

**Решение.** `ActionCode` — перечисление, реализуемое через
`AccessibilityService.performGlobalAction`:

| № | Действие | Константа | API |
|---|---|---|---|
| 1 | Назад | `GLOBAL_ACTION_BACK` | 16 |
| 2 | Домой | `GLOBAL_ACTION_HOME` | 16 |
| 3 | Недавние | `GLOBAL_ACTION_RECENTS` | 16 |
| 4 | Шторка уведомлений | `GLOBAL_ACTION_NOTIFICATIONS` | 16 |
| 5 | Быстрые настройки | `GLOBAL_ACTION_QUICK_SETTINGS` | 16 |
| 6 | Меню питания | `GLOBAL_ACTION_POWER_DIALOG` | 16 |
| 7 | Блокировка экрана | `GLOBAL_ACTION_LOCK_SCREEN` | 28 |
| 8 | Скриншот | `GLOBAL_ACTION_SCREENSHOT` / `TAKE_SCREENSHOT` | 28 / 34 |
| — | Нет действия | — | — |

**Обработка результата.** `performGlobalAction` возвращает `Boolean`; вызов может бросить
исключение на OEM-прошивке. Поэтому:

1. Вызов оборачивается в `try/catch`.
2. `false` или исключение → запись в диагностику (`ACTION_FAILED`) и понятное сообщение
   пользователю через `Toast` (стандартный Toast не требует `POST_NOTIFICATIONS`).
3. Сообщение rate-limited (не чаще раза в 2 секунды), чтобы не заспамить экран.
4. Приложение **не падает** и не повторяет действие автоматически.
5. Если действие недоступно на данной прошивке, UI может пометить его как
   «не поддерживается» после первого отказа (сохраняется в памяти сессии).

**Расширяемость.** `ActionDispatcher` — интерфейс. `GlobalActionDispatcher` реализует
встроенные действия; позже можно добавить `UserActionDispatcher` (Shizuku/Intent) и
пользовательские действия, не меняя `RemapEngine`. `ActionCode` при этом расширяется
новыми значениями, а JSON-кодек знает, как их читать.

**Ограничение.** Глобального действия «вперёд» **не существует**. Браузерный «forward»
без root/Shizuku недоступен; варианты и эксперимент S3 — в D-021. В v1 его нет, и UI не
должен его обещать.

**Следствия.** Для второй боковой кнопки — любое из восьми действий (например,
«Недавние»). Проверка `LOCK_SCREEN`/`SCREENSHOT` на HyperOS обязательна в M2: OEM может
ограничивать.

## D-011 — Профили: именованные в v1, привязка к приложению — M3

**Статус:** Accepted (подтверждено пользователем 2026-11-11)

**Контекст.** Пользователю нужны разные наборы действий: «браузер», «чтение», «работа».
В v1 профили должны создаваться, переименовываться, удаляться и переключаться вручную.
Автоматическая привязка к приложениям откладывается, но архитектура должна быть готова.

**Решение для v1.**
- Профиль = `id`, `name`, список `Mapping`.
- `Mapping` = `deviceDescriptor?`, `Chord`, `ActionCode`, `enabled`.
- Каждый профиль хранит **собственные** маппинги.
- Пользователь может: создать, переименовать, удалить, выбрать активный.
- Есть профиль по умолчанию (`default_profile_id`); его нельзя удалить.
- Удаление активного профиля переключает на профиль по умолчанию.
- Список целевых устройств (`targets`) — общий для приложения, не per-profile.
  (Per-profile targets — возможное расширение, не v1.)
- `appBindings` в v1 пуст; `foregroundPackage` не используется для выбора профиля.

**Решение для M3 (per-app).**
- `appBindings: Map<package, profileId>`.
- Приоритет разрешения:
  1. привязка foreground-пакета;
  2. активный профиль;
  3. `default_profile_id`;
  4. нет маппинга → pass.
- Foreground-пакет берётся из `TYPE_WINDOW_STATE_CHANGED` (`event.packageName`), без
  чтения содержимого окон (`canRetrieveWindowContent="false"`).
- Привязка задаётся вручную (выбор из недавних foreground-пакетов или ввод пакета), без
  `QUERY_ALL_PACKAGES`.

**Следствия.** Разрешение профиля — O(1) по предвычисленным картам. Смена профиля между
DOWN и UP не ломает аккорд: UP поглощается трекером независимо от конфига. Поле
`appBindings` присутствует в схеме с v1, но пустое — миграция в M3 не потребуется.

## D-012 — `onMotionEvent` / `setMotionEventSources` не используем

**Статус:** Accepted

**Контекст.** Казалось бы, `setMotionEventSources(SOURCE_MOUSE)` позволяет увидеть кнопки
мыши. Но API не предоставляет режим «наблюдать и пропустить дальше»: события, попавшие в

- Средняя/боковые кнопки как `MotionEvent` недоступны для ремапа.
- Любой будущий ремап кнопок мыши требует инъекции событий (root/Shizuku) — отдельный
  проект.

## D-013 — Shizuku не является обязательной зависимостью

**Статус:** Accepted (v1)

**Контекст.** Shizuku — отдельное приложение, которое поднимает процесс с shell-UID и даёт
обычным приложениям выполнять привилегированные операции через binder. Оно могло бы дать
`input keyevent`/`input keycombination`, app-specific действия и, возможно, «вперёд». Но
это отдельная установка, беспроводная отладка, разрешения и повышенная ответственность.

**Решение.** В v1 Shizuku нет: ни SDK, ни проверок, ни упоминаний в UI как обязательного
условия. Архитектура оставляет точку расширения: `ActionDispatcher` — интерфейс, одну из
реализаций можно добавить позже.

**Что Shizuku потенциально даёт (не проверено):**

| Возможность | Реалистичность | Комментарий |
|---|---|---|
| `input keyevent` / `input keycombination` | Высокая | Shell-UID; но нужной клавиши «forward» не существует, только комбинации |
| Браузерный «вперёд» через `Alt+Right` | Средняя | Зависит от браузера и версии Android; проверять в S3 |
| `INJECT_EVENTS` напрямую | Низкая | Signature-разрешение; shell не может выдать его обычному приложению |
| App-specific действия (Intent) | Средняя | Часть интентов доступна и без Shizuku, но фон ограничен |
| Ремап средней кнопки | Низкая | Нужен `onMotionEvent` + инъекция; риск сломать курсор |

**Следствия.** v1 полностью работает без Shizuku. Spike S3 оценивает выгоду и цену;
решение о включении — отдельно, после отчёта. Shizuku не должен становиться скрытым
обязательным условием ни в одной функции v1.

## D-015 — Обнаружение устройств через `InputManager.InputDeviceListener`

**Статус:** Accepted

**Контекст.** S1 опрашивал устройства раз в 3 секунды. Для продукта это лишние
пробуждения и задержка в UI.

**Решение.** Начальная энумерация `inputManager.inputDeviceIds` + подписка
`registerInputDeviceListener` (API 16). События `onInputDeviceAdded/Removed/Changed`
обновляют `StateFlow` каталога. Фильтр: источники содержат `SOURCE_MOUSE` или

**Следствия.** UI видит подключение/отключение сразу. `descriptor` сохраняется в
`TargetDevice`; при повторном подключении привязка не слетает.

## D-016 — Репозиторий: продукт в корне, спайки в `spikes/s1/` и `spikes/s2/`

**Статус:** Accepted (подтверждено пользователем 2026-11-11)

**Контекст.** Сейчас корень — это Gradle-проект S1. Продукт должен занять корень, а
доказательные спайки — сохраниться как отдельные сборки. Пользователь требует резервную
копию, первый commit до изменений, проверку сборки спайков после переноса и отчёт.

**Решение.**

1. **Резервная копия.** Создать `<repo-parent>/<repo-name>-backup-<YYYYMMDD-HHMMSS>` —
   копию исходников и документации без `build/`, `.gradle/`, `local.properties`. Сверить
   количество файлов и ключевые хэши. Копия остаётся до отдельного подтверждения.
2. **Git.** `git init`, `.gitignore` (`build/`, `.gradle/`, `local.properties`, `*.apk`,
   `.idea/`), первый commit: «baseline: S1 + S2 + docs». Это вторая страховка.
3. **Перенос S1.** Скопировать проект S1 целиком в `spikes/s1/` (включая `app/`,
   `settings.gradle.kts`, `build.gradle.kts`, wrapper, `gradle.properties`,
   `local.properties` для сборки).
4. **Перенос S2.** Скопировать `spike-s2/` в `spikes/s2/` целиком (включая
   `local.properties`).
5. **Проверка.** Собрать `spikes/s1` и `spikes/s2` старыми командами. Только после
   успешной сборки убрать дубликаты из корня (перенос считается завершённым).
   Безвозвратного удаления нет: оригиналы остаются в резервной копии и в git-истории;
   резервная копия не удаляется без отдельного подтверждения.
6. **Продукт.** В корне — новый проект: `settings.gradle.kts` (`include(":app")`),
   `build.gradle.kts`, wrapper 8.14.6, новый `app/` с `namespace = "com.mousemanager"`,
   `local.properties` (не коммитить).
7. **Изоляция.** `spikes/*` — независимые сборки, корневой Gradle их не включает.
8. **Отчёт.** Показать `git status`, дерево каталогов, результаты сборки S1/S2 и сборки
   пустого продукта.
9. **Запрет.** Не переписывать историю, не редактировать содержимое спайков, не удалять
   резервную копию без подтверждения.

**Следствия.** `.\gradlew.bat :app:assembleDebug` в корне собирает продукт. Спайки
собираются каждый в своей папке. Перенос — управляемый: копия → проверка → удаление
оригинала. Если сборка спайка после копирования не проходит, оригинал не трогаем и
разбираемся.

**Уточнения от 2026-11-11 (см. D-022).** Из резервной копии исключается также `.kotlin/`;
в копию добавляются `_artifacts/` с APK S1/S2 и `README-restore.txt`; `.gitignore`
дополнен (`.kotlin/`, `*.jks`, `*.keystore`, `Thumbs.db`); до первого commit локально
`core.autocrlf=false`; существующий корневой wrapper 8.14.6 сохраняется; старые кэши не
удаляются; копии спайков сверяются с оригиналами по SHA-256 до удаления дубликатов; дата
начала M0 не назначена. Остальные пункты D-016 в силе.

## D-017 — Диагностика: кольцевой буфер в памяти

**Статус:** Accepted

**Контекст.** Нужно объяснять решения и ловить регрессии, но писать логи в файл и
просить доступ к хранилищу не хочется.

**Решение.** Кольцевой буфер на 500 `KeyRecord` в памяти процесса, `StateFlow` для UI.
Поля: время, `deviceId`, имя, `descriptor`, `keyCode`, `scanCode`, `metaState`,
`repeatCount`, `decision`, `isTarget`, `armed`. Отдельно — история `deviceId` по
`descriptor` (доказательство нестабильности).

`Decision`: `CONSUMED`, `PASSED_DISARMED`, `PASSED_FOREIGN_DEVICE`, `PASSED_MODIFIER`,
`PASSED_NO_MAPPING`, `PASSED_NON_HARDWARE`, `PASSED_ERROR`.

> В S2 тот же вердикт печатался как `PASSED_OTHER_DEVICE`; S2 заморожен и не
> переименовывается (`SPIKES.md` §5).

`Log.d` — только в `DEBUG`, тег `MouseManager`.

**Следствия.** Журнал теряется при смерти процесса — для диагностики достаточно.
Экспорт в файл — опционально в M4.

## D-018 — Fail-safe: поведение при сбоях

**Статус:** Accepted

**Контекст.** Глобальный фильтр клавиш — опасный механизм. Любая ошибка не должна
блокировать ввод. Пользователь отдельно попросил описать аварию, перезапуск службы,
отключение мыши и недоступность DataStore.

**Главный принцип.** Худший допустимый сценарий — «перехват не работает, но ввод цел».
Обратный сценарий («ввод сломан, зато перехват работает») недопустим.

### 18.1 Инварианты горячего пути

1. Нет службы/подключения → перехвата нет.
2. `armed == false` → pass (кроме pending UP, см. п. 10).
3. `targets` пуст → pass.
4. `descriptor == null` → pass.
5. `descriptor` не в `targets` → pass.
6. Клавиша не является триггером маппинга → pass.
7. Модификатор → pass (только отслеживается).
8. Ошибка парсинга/загрузки конфига → `armed=false`, fail-safe снимок, pass.
9. Исключение в `onKeyEvent` → лог, `setArmed(false)`, `return false`.
10. `ACTION_UP`, для которого есть pending поглощённого DOWN → `Consume` **до** проверки
    `armed`/`targets`, чтобы выключение перехвата не оставляло половину аккорда.
11. `ACTION_UP` без pending → pass.
12. Repeat триггера → `Consume` без повторного dispatch.
13. Исключение в `ActionDispatcher` → лог, сообщение, без падения и без retry.

### 18.2 Аварийное завершение приложения

- `armed` — runtime-флаг (D-006), поэтому смерть процесса всегда оставляет `false`.
- Служба, перезапущенная системой, поднимается с `armed=false`; перехвата нет.
- Незавершённый аккорд: `C↓` мог быть поглощён, `C↑` уйдёт в приложение как сиротский.
  Буква не «залипнет», потому что приложение не видело DOWN.
- Действие, не успевшее выполниться, просто не выполняется; это безопаснее, чем
  блокировка ввода.
- Отдельный crash-guard не нужен; для диагностики можно писать маркер, но он не влияет
  на безопасность.

### 18.3 Перезапуск/переподключение службы

- `onServiceConnected` вызывается повторно → сбросить `ChordTracker`, перечитать конфиг,
  заново применить `FLAG_REQUEST_FILTER_KEY_EVENTS`, опубликовать статус.
- `armed=false` при каждом подключении (D-006).
- Если `filterApplied=false` (система не приняла флаг) → `armed=false` и явное
  предупреждение в UI: «служба подключена, но фильтр клавиш не принят».
- `onUnbind`/`onDestroy` → отменить корутины, сбросить трекер, опубликовать «остановлена».
- Если служба отключена в настройках, события не приходят; UI показывает инструкцию.

### 18.4 Отключение мыши

- Событий от `descriptor` больше нет; pending UP истекает через 1500 мс.
- Привязка в настройках сохраняется; при повторном подключении с тем же `descriptor`
  маппинг работает без действий пользователя.
- Если мышь подключилась с другим `descriptor` (другой порт/хаб), привязка не совпадёт;
  UI показывает «не подключено» и предлагает выбрать заново.
- Если отключение случилось между `C↓` и `C↑`, `C↓` уже поглощён, `C↑` не придёт.
  Залипания нет; действие либо выполнилось, либо нет — оба варианта безопасны.
- `Ctrl↓` без `Ctrl↑` из-за отключения мыши — это возможный «залипший» Ctrl на стороне
  системы (мы не можем синтезировать UP). Лечится нажатием/отпусканием Ctrl на
  клавиатуре или переподключением; фиксируется в диагностике.

### 18.5 DataStore недоступен, повреждён или медленный

| Ситуация | Поведение |
|---|---|
| Файл повреждён / JSON не парсится | Fail-safe снимок: `armed=false`, `targets=emptySet`, default-профиль; pass; UI показывает ошибку и кнопку «Сбросить настройки» |
| `schema_version` новее приложения | Режим только чтения, `armed=false`, сообщение «обновите приложение» |
| Ошибка записи | UI показывает «не удалось сохранить»; в памяти остаётся последний хороший снимок; перехват не ломается |
| DataStore завис/медленный | Горячий путь его не читает; перехват работает по последнему снимку; UI может показать устаревшие данные |
| Второй экземпляр DataStore | Не допускается: singleton в `MouseManagerApp`; при ошибке — fail-safe |
| Ключа нет | Значение по умолчанию; это не ошибка |
| Неизвестное действие в JSON | `NONE` + предупреждение; остальной конфиг валиден |
| Неизвестный `descriptor` в маппинге | Маппинг сохраняется: устройство может подключиться позже |
| Файл не перезаписывается автоматически | Повреждённые данные сохраняются для диагностики до явного сброса |

### 18.6 Смена фокуса и окна

- `onKeyEvent` глобальный: потеря фокуса не прекращает события.
- Действие выполняется на DOWN, немедленно; смена foreground-приложения за ~100 мс
  теоретически возможна, практически исключена.
- Pending UP привязан к устройству и keyCode, не к окну; смена окна не мешает поглотить UP.
- В режиме захвата аккорда (`CaptureController`) есть таймаут 10 с и отмена при уходе с
  экрана.

### 18.7 Сбой действия

- `performGlobalAction` вернул `false` или бросил исключение → `ACTION_FAILED` в
  диагностике, Toast, rate-limit 2 с, без падения и без retry.
- Если действие не поддерживается на прошивке, UI может пометить его как недоступное
  в текущей сессии.

**Следствия.** Любой отказ ведёт к pass или к явному сообщению. Пользователь никогда не
остаётся с заблокированным вводом без объяснения.

## D-021 — Действие «вперёд»: что возможно, что нет, и что проверять в S3

**Статус:** Open (исследование S3; в v1 действия нет)

**Контекст.** Пользователь просил не закрывать возможность «вперёд» окончательно.
Нужно честно разделить: что дают публичные API, что потенциально даёт Shizuku, что
требует отдельного эксперимента.

### 21.1 Публичные Android API

| Подход | Что делает | Годится для «вперёд»? |
|---|---|---|
| `performGlobalAction(GLOBAL_ACTION_BACK)` | Системный «назад» | Да, для «назад». Для «вперёд» action нет |
| `performGlobalAction(GLOBAL_ACTION_*)` | HOME, RECENTS, NOTIFICATIONS, QUICK_SETTINGS, POWER_DIALOG, LOCK_SCREEN, SCREENSHOT | Нет |
| `dispatchGesture(...)` | Синтез касаний/свайпов | Скорее нет: в Chrome Android нет стандартного жеста «вперёд»; проверять |
| `AccessibilityNodeInfo.performAction(ACTION_SCROLL_FORWARD)` | Прокрутка focused-узла | Нет: это скролл, не история |
| Клик по кнопке «вперёд» в UI браузера | `AccessibilityNodeInfo` + `performAction(ACTION_CLICK)` | Хрупко: зависит от браузера, языка, видимости панели; только эксперимент |
| `Intent`/deep link | Открыть URL | Нет: не управляет историей текущей вкладки |
| `Instrumentation.sendKeySync` / инъекция клавиш | Синтез `Alt+Right` | Нет: требует `INJECT_EVENTS` (signature), обычному приложению недоступно |
| `GLOBAL_ACTION_DPAD_RIGHT` (API 31) | DPAD-событие | Нет: двигает фокус, не историю |
| `KEYCODE_NAVIGATE_NEXT` / `PREVIOUS` | Навигация в приложении | Нет: требует инъекции, поведение зависит от приложения |

**Вывод по публичным API:** надёжного «вперёд» нет. `GLOBAL_ACTION_BACK` — единственное
гарантированное навигационное действие.

### 21.2 Shizuku (потенциально)

Shizuku даёт процесс с shell-UID и возможность выполнять shell-команды. Это может дать:

1. **`input keycombination`** (если поддерживается на API 35) — отправить `Alt+Right` или
   `Ctrl+Right` в foreground-приложение. Сработает ли «вперёд» в Chrome/Edge — зависит от
   браузера и версии; **не проверено**.
2. **`input keyevent`** — отправка отдельных клавиш; для «вперёд» нужной клавиши нет,
   только комбинация.
3. **Прямой `INJECT_EVENTS`** — маловероятно: разрешение signature; shell-UID не может
   выдать его обычному приложению.
4. **App-specific Intent** — некоторые браузеры поддерживают свои действия, но это не
   универсально и требует знания пакета.

**Вывод по Shizuku:** возможен узкий, браузерозависимый вариант. Не обещать
работоспособность до S3. Shizuku не должен становиться обязательным для базовых функций.

### 21.3 Эксперимент S3

| № | Гипотеза | Метод | Критерий успеха |
|---|---|---|---|
| S3-1 | `performGlobalAction` не даёт «вперёд» | Перебрать все константы на HyperOS 3 | Подтвердить отсутствие; зафиксировать, какие действия работают |
| S3-2 | `dispatchGesture` не даёт forward в Chrome | Свайпы разных направлений в Chrome/Edge | Если forward — задокументировать; иначе закрыть |
| S3-3 | Клик по кнопке forward в UI браузера возможен | Найти узел по contentDescription/ID, кликнуть | Работает в 1–2 браузерах; оценить хрупкость |
| S3-4 | Shizuku + `input keycombination Alt+Right` даёт forward | Установить Shizuku, выполнить команду в Chrome/Edge | Навигация вперёд в хотя бы одном браузере |
| S3-5 | Shizuku + `input keyevent` для других действий | Проверить `KEYCODE_*` | Понять, какие действия доступны |
| S3-6 | `INJECT_EVENTS` через Shizuku | Попытка `pm grant` / binder | Почти наверняка нет; зафиксировать |
| S3-7 | Средняя кнопка через `onMotionEvent` + инъекция | Забрать события, вернуть инъекцией | Курсор не ломается; иначе закрыть |

**Решение по итогам S3:** либо в v2 появляется `ShizukuActionDispatcher` с явной пометкой
«требует Shizuku», либо «вперёд» остаётся недоступным и UI честно это показывает.

**Следствия для v1.** Действия «вперёд» нет. `ActionDispatcher` расширяемый, `ActionCode`
можно дополнить. В UI — пояснение, что «вперёд» появится только после отдельного
эксперимента, если появится вообще.

## D-022 — M0: уточнения предпускового плана

**Статус:** Accepted (подтверждено пользователем 2026-11-11)

**Контекст.** 2026-11-11 проведена предпусковая проверка M0. Структура подтверждена:
`.git` и `spikes/` отсутствуют, резервная копия не создавалась, S1 — в корне
(`app/`, `com.mousemanager.diagnostics`), S2 — в `spike-s2/`
(`com.mousemanager.spike.s2`). Исходники без кэшей — 69 файлов, 0.35 МБ; всё остальное
(1265 файлов, 112 МБ) — регенерируемые `build/`, `.gradle/`, `.kotlin/`. Пользователь
принял уточнения к D-016.

**Решение.**

1. **APK в резервной копии.** Оба текущих APK копируются в `_artifacts/`
   (`s1-app-debug.apk`, `s2-app-debug.apk`), потому что `build/` из копии исключён, а APK
   S2 — вещественное доказательство приёмки S2. SHA-256 сверяется отдельно.
2. **Исключения копии:** `build/`, `.gradle/`, `.kotlin/`, `.idea/`, `local.properties`,
   `_artifacts/` (для сверки). `.kotlin/` добавлен к списку D-016.
3. **`.gitignore` дополнен:** `.kotlin/`, `*.jks`, `*.keystore`, `Thumbs.db` (остальные
   правила уже были).
4. **`core.autocrlf`.** Системный `gitconfig`
   (`C:/Program Files/Git/etc/gitconfig`) задаёт `core.autocrlf=true`. До первого commit
   локально выставляется `git config --local core.autocrlf false`, иначе индекс
   нормализует переводы строк и требование «побайтово не изменены» теряет смысл.
5. **Wrapper.** Существующий корневой wrapper 8.14.6 (official bin) сохраняется и
   используется продуктом; заново не генерируется.
6. **Кэши.** `build/`, `.gradle/`, `.kotlin/` в корне пока не удаляются. При проблемах
   сборки — сначала сообщить пользователю и запросить разрешение.
7. **Оригиналы S1/S2** остаются на месте, пока не пройдены обе проверки: SHA-256 копий
   совпал с оригиналами **и** обе сборки в `spikes/*` успешны. Только после этого
   удаляются дубликаты из корня.
8. **Git-идентичность.** Проверена, менять не требуется: глобально
   `user.name = Jaba-Script`, `user.email = 178173545+Jaba-Script@users.noreply.github.com`; `git var
   GIT_AUTHOR_IDENT` резолвится в `Jaba-Script <178173545+Jaba-Script@users.noreply.github.com>`; подпись
   коммитов (`commit.gpgsign`) не включена. Глобальные настройки не изменяются.
   Системный `init.defaultBranch = master`.
9. **Дата начала M0 не назначена.** В документах она определяется в момент отдельного
   подтверждения; прежняя формулировка «план на 2026-11-12» отменена.

### 22.1 Метод проверки резервной копии

Проверка — до любых перемещений; любая ошибка чтения или копирования означает остановку,
а не пропуск файла: иначе потеря останется незамеченной. Сравниваются пары `Rel` + `Size` +
`Hash`; пустой или некорректный SHA-256 (не 64 hex) — ошибка, а не «совпадение».
`README-restore.txt` и `_manifest-*` в сверку не входят (создаются после).

Скрипты проверки, эталонные хэши APK и порядок этапов сохранены дословно в
`docs/archive/M0-runbook.md`. Ожидалось 67 / 67 файлов (до M0).

### 22.2 `README-restore.txt`

Создаётся вместе с копией и в сверку не входит: фактический путь и время копии, что вошло
и что нет (`build/`, `.gradle/`, `.kotlin/`, `.idea/`, `local.properties`), порядок
восстановления, сверка с `_manifest-sha256.csv`, APK в `_artifacts/` как артефакты S1/S2.

### 22.3 Следствия

- Резервная копия полностью воспроизводима и проверяема без доверия к логам robocopy.
- APK S2 сохраняется как доказательство, даже если `build/` будет пересоздан.
- Если копия спайка или её сборка не совпали с оригиналом — M0 останавливается,
  оригиналы не трогаются.
- Уточнения не меняют архитектуру продукта; затрагивают только процесс M0.

## D-023 — M0: факты и решения, принятые при выполнении

**Статус:** Accepted (2026-11-11, по результатам этапов 1–7)

**Контекст.** M0 выполнен по D-016/D-022. По ходу возникли четыре вопроса, решения по
которым фиксируются здесь, чтобы не переобсуждать их в M1.

**Решение.**

1. **Скелет продукта.** Минимальный Compose-скелет: `MainActivity`, тема, строки; без
   службы, DataStore, иконки и лишних зависимостей. Корневые `build.gradle.kts`,
   `settings.gradle.kts`, `gradle.properties` и wrapper 8.14.6 переиспользованы без
   изменений — они уже соответствовали продукту (AGP 8.13.2, Kotlin 2.3.21,
   `include(":app")`). Иконка — M1/M4.
2. **История Git.** Один коммит «reorg: product root, spikes archived» (D-016). Пять
   путей S1 (`app/build.gradle.kts`, `proguard-rules.pro`, `AndroidManifest.xml`,
   `res/values/strings.xml`, `res/values/themes.xml`) переиспользованы продуктом, поэтому
   в истории они выглядят как `M`, а не `D`+`A`. Осознанный компромисс: итоговое дерево
   корректно, дробить коммит ради косметики истории не стали. По той же причине 47 файлов
   архива при выводе `git show` могут отображаться как переименования (`R100`,
   `app/…` → `spikes/s1/…`, `spike-s2/…` → `spikes/s2/…`), а не как пары `D`+`A`: это
   поведение отображения, содержимое и дерево корректны (`--no-renames` даёт `D`+`A`).
3. **APK и воспроизводимость.** `spikes/s2` собрался бит-в-бит (`FAA8435A…`). APK S1
   отличается от эталона на 40 579 байт, но payload идентичен (132 записи, те же сжатые
   размеры); разница — мёртвый padding инкрементальной сборки: 35 703 байта между
   `classes3.dex` и `classes8.dex`, 1 839 — между `classes4.dex` и `classes5.dex`,
   3 037 — лишний extra в local header `lib/arm64-v8a/libandroidx.graphics.path.so`.
   Вывод: побайтовое сравнение debug-APK корректно только для одинакового пути сборки;
   критерий приёмки — успешная сборка, а не совпадение хэша.
4. **Разрешения в APK.** AndroidX Core автоматически объявляет
   `com.mousemanager.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`. Это его собственное
   signature-разрешение для runtime-ресиверов, а не запрос доступа; считать нормой.

**Следствия.** M1 стартует с пустого, но собираемого продукта; `spikes/*` — архив
доказательств, в корневую сборку не входят; проверки APK в дальнейшем не требуют
побайтового совпадения с эталоном.

## D-024 — `org.json` для JVM-тестов кодека

**Статус:** Accepted (подтверждено пользователем 2026-11-12)

**Контекст.** `ConfigCodec` использует `org.json` (D-007). В локальных JVM unit-тестах
Android подставляет заглушки: методы `JSONObject`/`JSONArray` возвращают `null`/`0` или
бросают «not mocked», поэтому round-trip и разбор неизвестного действия проверить нельзя.
Отклонены: `isReturnDefaultValues = true` (тесты проверяли бы заглушки, а не код) и
инструментальные `androidTest` (устройство нужно на каждый прогон).

**Решение.** В `testImplementation` добавляется `org.json:json:20240303` — эталонная
реализация того же API. Разрешено **только** для JVM-тестов.

**Ограничения.**

1. `implementation`/`runtimeOnly` для `org.json` запрещены: Android предоставляет этот API
   сам, дублирование в APK недопустимо.
2. Версия фиксируется явно; обновление — вместе с изменением `ConfigCodec`.
3. Зависимость не даёт права добавлять другие библиотеки: правило D-020 действует.

**Стоимость.** Около 80 КБ только в тестовом classpath: не входит в APK, `release`, R8 и
runtime; на размер и скорость сборки продукта не влияет.

**Следствия.** Список D-020 расширен этой записью — только для `testImplementation`.
`ConfigCodecTest` проверяет реальный JSON, а не заглушки Android.

## D-025 — Одна служба-фильтр клавиш в продуктовой конфигурации

**Статус:** Accepted (подтверждено пользователем 2026-11-13)

**Контекст.** На этапе S6 продуктовая `MouseManagerService` проверялась на планшете вместе
с включённой S2 (`com.mousemanager.spike.s2`). Обе службы запрашивали
`FLAG_REQUEST_FILTER_KEY_EVENTS` (`flags=0x20`). При нажатии боковых кнопок VXE R1SE+
доставка клавиш в окно приложения задерживалась на 505–558 мс. Продуктовая служба при этом
отвечала на `onKeyEvent` за 2–6 мс, а S2, будучи привязанной, не регистрировала события
в своём журнале.

**Решение.** В продуктовой конфигурации `FLAG_REQUEST_FILTER_KEY_EVENTS` запрашивает
**только** `MouseManagerService`. Вторая Accessibility-служба-фильтр не входит в продукт и
не должна работать одновременно с ним при пользовательском тестировании.

**Обоснование (A/B на устройстве, 2026-11-12/13).**

| Конфигурация | Ответ `onKeyEvent` | Доставка в окно |
|---|---|---|
| Mouse Manager + S2 | 2–6 мс | 505–558 мс |
| Только Mouse Manager | 3–18 мс | 6–28 мс |

- Задержка исчезла после отключения S2 при неизменных коде, фокусе и устройстве.
- В Telegram задержка появления вставленного текста после `Ctrl+V` также исчезла после
  отключения S2 (наблюдение пользователя).
- S2 была подключена (`hasBound=true`, `flags=20`), но её `onKeyEvent` не выполнялся:
  её лог, пишущий каждое событие безусловно, оставался пустым.
- A/B подтверждает зависимость задержки от S2. Точный внутренний механизм Android/HyperOS
  (ожидание ответа службы-фильтра с таймаутом около 500 мс) окончательно не установлен.

**Ограничения.**

1. S2 — исследовательский Spike (D-016) и не входит в продукт; её код не меняется.
2. В продуктовой конфигурации — ровно одна служба с `FLAG_REQUEST_FILTER_KEY_EVENTS`.
3. При пользовательском тестировании не запускать одновременно несколько
   Accessibility-служб-фильтров: это искажает задержку ввода.
4. D-014 не отменяется: флаг остаётся обязательным для продуктовой службы.

**Следствия.** Задержка ввода не является свойством продукта. Если у пользователя включена
другая служба-фильтр, поведение может ухудшиться — это внешнее условие, а не дефект
Mouse Manager. Проверка S6 выполнена в конфигурации «только Mouse Manager».
