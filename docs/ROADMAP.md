# ROADMAP — Mouse Manager

Версия: черновик для утверждения. Дата: **2026-11-11**.
Порядок этапов выбран так, чтобы каждая веха давала проверяемый результат на устройстве и
не требовала переписывать предыдущую.

```
M0  документация + реорганизация          (без кода продукта)
 │
M1  скелет приложения                     (сборка, служба, DataStore, каталог устройств)
 │
M2  ядро ремапа                           (аккорд → действие, мастер-переключатель)
 │
M3  профили                               (именованные + привязка к приложению)
 │
M4  безопасность, диагностика, полировка  (fail-safe, panic tile, release)
 │
 └─ S3 (опционально)  «вперёд» / инъекция / Shizuku
```

**Правило:** веха не начинается, пока предыдущая не принята на устройстве. Внутри вехи —
одна задача на сессию (см. `docs/WORKFLOW.md`).

## M0 — Документация и реорганизация

**Цель:** продукт получает чистый корень, спайки — предсказуемое место, появляется
страховка в виде git.

**Статус:** **завершён 2026-11-11**. План проверен и уточнён (D-022), выполнен этапами
1–7; итоги зафиксированы в **D-023** и `PROJECT_STATUS.md` (§1, §5, §9).

**Итог:** 2 коммита (`ecceb12` baseline и reorg HEAD), 82 файла в дереве; `spikes/s1`
и `spikes/s2` собираются (139 с и 107 с, APK S2 бит-в-бит), продукт собирается (145 с).

### Работы

1. **Резервная копия.** `D:\Projects\MouseManager-backup-<YYYYMMDD-HHMMSS>`: копия
   исходников и документации без `build/`, `.gradle/`, `.kotlin/`, `.idea/`,
   `local.properties` (ожидается 67 файлов, ~0.35 МБ). Сверить количество файлов,
   размер и SHA-256 каждого файла; ошибка чтения/хэширования — остановка, а не пропуск
   файла (D-022). Отдельно скопировать оба текущих APK в `_artifacts/`
   (`s1-app-debug.apk`, `s2-app-debug.apk`) и сверить их SHA-256 отдельно. Положить
   `README-restore.txt` с порядком восстановления.
2. `git init`. До первого commit: локально `git config --local core.autocrlf false`
   (системный `gitconfig` задаёт `true`, D-022) и `.gitignore` (`build/`, `.gradle/`,
   `.kotlin/`, `local.properties`, `*.apk`, `*.aab`, `.idea/`, `*.jks`, `*.keystore`,
   `Thumbs.db`). Первый commit: «baseline: S1 + S2 + docs».
3. Скопировать S1 в `spikes/s1/` (весь проект: `app/`, `settings.gradle.kts`,
   `build.gradle.kts`, wrapper, `gradle.properties`, `local.properties` для сборки).
   `docs/`, `AGENTS.md`, `opencode.jsonc` в спайк не копируются.
4. Скопировать `spike-s2/` в `spikes/s2/` (включая `local.properties`, без кэшей).
5. Сверить SHA-256 копий `spikes/s1`, `spikes/s2` с оригиналами. Затем **проверить
   сборку** `spikes/s1` и `spikes/s2` старыми командами. Оригиналы S1/S2 сохраняются,
   пока не пройдены обе проверки (хэши и сборка). Только после успеха убрать дубликаты
   из корня (перенос завершён). Безвозвратного удаления нет: оригиналы остаются в
   резервной копии и в git-истории; резервная копия не удаляется. Старые кэши
   `build/`, `.gradle/`, `.kotlin/` не удаляются; при проблемах со сборкой — сначала
   сообщить пользователю и запросить разрешение.
6. В корне создать новый проект продукта (существующий wrapper 8.14.6 сохраняется):
   - `settings.gradle.kts` с `include(":app")`;
   - `build.gradle.kts` (AGP 8.13.2, Kotlin 2.3.21, compose plugin);
   - wrapper 8.14.6;
   - новый `app/` с `namespace = "com.mousemanager"`;
   - `local.properties` с `sdk.dir=D:\\Android\\Sdk` (не коммитить).
7. Commit «reorg: product root, spikes archived».
8. Проверить, что `spikes/*` **не** попадают в корневую сборку.
9. Показать `git status`, дерево каталогов и результаты всех сборок.

### Критерии приёмки

- [x] Резервная копия создана и проверена (количество, размер, SHA-256 каждого файла).
- [x] Оба APK лежат в `_artifacts/`; их SHA-256 совпадают с исходными.
- [x] `README-restore.txt` присутствует в резервной копии.
- [x] `git log` содержит commit до переноса и commit после.
- [x] `git config --local core.autocrlf` = `false`.
- [x] Копии `spikes/s1`, `spikes/s2` побайтово совпали с оригиналами **до** удаления дубликатов.
- [x] Файлы S1/S2 побайтово не изменены (перенос, не правка).
- [x] `spikes/s1` и `spikes/s2` собираются после переноса.
- [x] Корневой `.\gradlew.bat :app:assembleDebug` собирает **пустой** продукт.
- [x] `git status` чистый, `local.properties` не в индексе.
- [x] Показаны `git status`, дерево, результаты сборок.

### Риски

| Риск | Смягчение |
|---|---|
| Перенос сломает пути в спайках | Спайки — независимые проекты; пути относительные, проверяем сборкой |
| Случайно закоммитить `local.properties` | `.gitignore` до первого commit |
| Потеря доказательств | Первый commit — до любых перемещений |
| APK не попадают в backup (исключён `build/`) | Копия обоих APK в `_artifacts/` + отдельная сверка SHA-256 (D-022) |
| Системный `core.autocrlf=true` искажает доказательства | Локально `core.autocrlf=false` до первого commit (D-022) |
| Стейл-кэши `build/`, `.gradle/`, `.kotlin/` мешают сборке продукта | Кэши не удаляются; при проблеме — сообщить и запросить разрешение |
| Ошибка чтения файла при сверке маскирует потерю | Хэш-скрипт падает на первой ошибке, а не пропускает файл (D-022) |

**Оценка:** 1 сессия.

## M1 — Скелет приложения

**Цель:** приложение собирается, устанавливается, служба включается и показывает статус,
но **ничего не перехватывает**.

### Работы

1. `MouseManagerApp`: инициализация DataStore, `SettingsRepository`, `DeviceCatalog`.
2. `MouseManagerService`: объявление в манифесте, `accessibility_service_config.xml`
   (D-014), `onServiceConnected` с применением флага, `ServiceState`.
3. `KeyEventMapper` и `KeyInput` (без логики решений).
4. `DeviceCatalog` + `InputDeviceListener` + UI-список устройств.
5. `SettingsRepository` + `ConfigCodec` + `ConfigStore` (чтение/запись, без маппингов).
6. UI-каркас: Home со статусом, Devices, About; тема Material3; строки в `strings.xml`.
7. Диагностический журнал: приём событий, `Decision=PASSED_*`, экран Diagnostics.
8. `RemapEngine`-заглушка: всегда `Pass(DISARMED)`.

### Критерии приёмки

- [ ] Сборка и установка проходят.
- [ ] Служба включается в настройках, `filterApplied=true` в UI.
- [ ] Мышь видна в Devices с `descriptor`.
- [ ] Переподключение мыши обновляет список без перезапуска приложения.
- [ ] Журнал показывает события мыши и других устройств с решениями `PASSED_*`.
- [ ] Ни одно событие не поглощается.
- [ ] Настройки (`targets`, профили) переживают перезапуск; `armed` — нет (D-006).

**Оценка:** 1–2 сессии.

## M2 — Ядро ремапа + именованные профили

**Цель:** боковая кнопка выполняет выбранное системное действие; всё остальное работает
как раньше. В v1 уже есть именованные профили с ручным переключением.

### Работы

1. `Chord`, `ChordKey`, `ActionCode`, `Verdict`, `PassReason`.
2. `ChordTracker` (модификаторы, pending UP, timeout).
3. `RemapEngine` (алгоритм §6) + `RuntimeConfig`.
4. `ConfigStore`: построение предвычисленных карт, `@Volatile` публикация.
5. `GlobalActionDispatcher` + проверка результата.
6. `SettingsRepository`: `targets`, `profiles`, маппинги. `armed` — только в памяти (D-006).
7. Профили v1: создание, переименование, удаление, ручное переключение, профиль по
   умолчанию, защита от удаления последнего. У каждого профиля — свои маппинги.
8. UI:
   - мастер-переключатель с предупреждением;
   - выбор целевых устройств;
   - экран профилей (CRUD + активный);
   - список маппингов активного профиля;
   - режим захвата аккорда (`CaptureController`);
   - выбор действия из таблицы D-010.
9. JVM-тесты на `RemapEngine`/`ChordTracker` (таблица §16.1).
10. Ручной чек-лист §16.2 на устройстве.

### Критерии приёмки

- [ ] Ctrl+C от VXE → выбранное действие (например, BACK), `CONSUMED` для C.
- [ ] Ctrl в журнале — `PASSED_MODIFIER`, клавиатура не затронута.
- [ ] Copy/paste этой мышью не срабатывают, пока перехват включён.
- [ ] Кнопки громкости работают; полноценная клавиатура — по чек-листу §16.2, п. 13
      (непроверенное условие до появления железа).
- [ ] Переподключение мыши сохраняет привязку.
- [ ] Выключение перехвата возвращает штатное копирование.
- [ ] Повторный запуск/переподключение службы → `armed=false` (D-006).
- [ ] Профили: создать, переименовать, удалить, переключить; у каждого свои маппинги;
      последний/дефолтный профиль защищён.
- [ ] Все 8 действий проверены; при `false`/исключении — сообщение, без падения.
- [ ] Все unit-тесты зелёные.

**Оценка:** 2–3 сессии.

## M3 — Привязка профилей к приложениям (после v1)

**Цель:** автоматически выбирать профиль по foreground-приложению. Именованные профили,
CRUD и ручное переключение уже сделаны в M2; здесь добавляется только автоматика.

### Работы

1. `appBindings` + foreground-пакет из `TYPE_WINDOW_STATE_CHANGED`.
2. Разрешение профиля (привязка → активный → default → pass).
3. UI привязок: выбор из недавних foreground-пакетов или ручной ввод, без
   `QUERY_ALL_PACKAGES`.
4. Копирование профиля (опционально).
5. Тесты разрешения профиля.

### Критерии приёмки

- [ ] Привязка пакета: при переходе в приложение действует его профиль.
- [ ] Без привязки — активный профиль; без активного — default.
- [ ] Ошибка в привязке не ломает перехват (fallback).
- [ ] Unit-тесты на приоритеты.
- [ ] Ручное переключение по-прежнему работает и перекрывает привязку? (решить в M3:
      приоритет привязки или ручного выбора — зафиксировать в ADR).

**Оценка:** 1–2 сессии.

## M4 — Безопасность, диагностика, полировка

**Цель:** приложением можно пользоваться ежедневно и не бояться «залипшего» перехвата.

### Работы

1. Проверить crash-safe поведение D-006: падение, kill системой, перезапуск службы,
   перезагрузка → `armed=false`. Отдельный crash-guard не нужен.
2. Panic: Quick Settings tile (опционально, по ответу пользователя) + уведомление о
   включённом перехвате (если решим).
3. Экран Diagnostics: `appliedFlags`, история `deviceId`, фильтры, «сбросить журнал».
4. Обработка всех fail-safe сценариев D-018/§14 + тесты: повреждённый DataStore, ошибка
   записи, потеря мыши между DOWN и UP, сбой `performGlobalAction`.
5. R8/release: проверить, что служба, JSON и Compose не сломались; включить minify.
6. Полировка UI: пустые состояния, подтверждения, тексты, доступность.
7. Финальный ручной чек-лист на чистой установке.
8. Обновить `docs/PROJECT_STATUS.md` и `DECISIONS.md` по фактическим решениям.

### Критерии приёмки

- [ ] Падение/перезапуск не оставляет перехват включённым (D-006).
- [ ] `armed=false` после перезапуска службы и перезагрузки.
- [ ] Повреждённый/недоступный DataStore не блокирует ввод.
- [ ] Ошибка действия показывает сообщение и не роняет приложение.
- [ ] Release APK собирается и проходит чек-лист.
- [ ] Пользователь может выключить перехват за одно действие.
- [ ] Документация соответствует коду.

**Оценка:** 1–2 сессии.

## S3 (опционально) — «Вперёд» и инъекция

**Цель:** выяснить, можно ли получить браузерный «вперёд» и app-specific действия без
root, и стоит ли вводить Shizuku.

### Гипотезы для проверки

1. `performGlobalAction` не даёт «вперёд» — подтвердить перебором.
2. `GLOBAL_ACTION_DPAD_*` (API 31) не заменяет «вперёд» в браузере.
3. `dispatchGesture` (свайп) не даёт forward в Chrome/Edge.
4. Shizuku (`Shizuku.newProcess` + `input keyevent`) даёт `Alt+Right` / нужную комбинацию.
5. `INJECT_EVENTS` через Shizuku: какие ограничения на HyperOS 3.
6. Средняя кнопка через `onMotionEvent` + инъекция: сохраняется ли курсор.

### Результат

Короткий отчёт с таблицей «гипотеза → результат → цена». Решение о Shizuku — отдельно,
не автоматически.

**Оценка:** 1 сессия + живой тест.
