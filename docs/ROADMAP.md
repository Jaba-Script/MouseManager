# ROADMAP — Mouse Manager

Версия: 1.0 (действует). Дата: **2026-11-11**.
Порядок этапов выбран так, чтобы каждая веха давала проверяемый результат на устройстве и
не требовала переписывать предыдущую.

```
M0  документация + реорганизация          (без кода продукта)
 │
M1  скелет приложения                     (сборка, служба, DataStore, каталог устройств)
 │
M2  ядро ремапа                           (аккорд → действие, мастер-переключатель)
 │
M3  профили                               (именованные + привязка к приложению)
 │
M4  безопасность, диагностика, полировка  (fail-safe, panic tile, release)
 │
 └─ S3 (опционально)  «вперёд» / инъекция / Shizuku
```

**Правило:** веха не начинается, пока предыдущая не принята на устройстве. Внутри вехи —
одна задача на сессию (см. `docs/WORKFLOW.md`).

## M1 — Скелет приложения

**Статус: принята 2026-11-13 (S8).** Результаты — `docs/S7-DEVICE-CHECKLIST.md`.

**Цель:** приложение собирается, устанавливается, служба включается и показывает статус,
но **ничего не перехватывает**.

### Работы

1. `MouseManagerApp`: инициализация DataStore, `SettingsRepository`, `DeviceCatalog`.
2. `MouseManagerService`: объявление в манифесте, `accessibility_service_config.xml`
   (D-014), `onServiceConnected` с применением флага, `ServiceState`.
3. `KeyEventMapper` и `KeyInput` (без логики решений).
4. `DeviceCatalog` + `InputDeviceListener` + UI-список устройств.
5. `SettingsRepository` + `ConfigCodec` + `ConfigStore` (чтение/запись, без маппингов).
6. UI-каркас: Home со статусом, Devices, About; тема Material3; строки в `strings.xml`.
7. Диагностический журнал: приём событий, `Decision=PASSED_*`, экран Diagnostics.
8. `RemapEngine`-заглушка: всегда `Pass(DISARMED)`.

### Критерии приёмки

- [x] Сборка и установка проходят.
- [x] Служба включается в настройках, `filterApplied=true` в UI.
- [x] Мышь видна в Devices с `descriptor`.
- [x] Переподключение мыши обновляет список без перезапуска приложения.
- [x] Журнал на устройстве показывает события мыши с решениями `PASSED_*`; другие устройства — по S6; физическая клавиатура — SKIP.
- [x] Ни одно событие не поглощается.
- [x] Сохранение `targets` после перезапуска проверено вручную в S8.4; профили вручную не проверялись; `armed` не сохраняется (D-006).

**Оценка:** 1–2 сессии.

### Уточнения (M2.0.1–M2.0.2)

**Повторный DOWN и timeout (D-026).** Pending хранится по `(descriptor, keyCode)`; один
DOWN — не более одного dispatch. Повторный DOWN/repeat при pending → `Consume` без
dispatch; repeat без pending → `Pass(REPEAT_OF_UNKNOWN)`. Окно — 1500 мс от последнего
события по этой клавише (скользящее), время обновляется через `max`, `expire` монотонен.
Проверка pending — до `armed`/`targets`/конфига: выключение перехвата, смена профиля или
удаление устройства из целей не оставляют половину аккорда. Абсолютного потолка и
tombstone нет; опоздавший UP проходит как `Pass(KEY_UP)` (сиротский UP безвреден, D-005).

**SCREENSHOT.** `GLOBAL_ACTION_TAKE_SCREENSHOT` (значение 9, API 28). При `minSdk 29`
проверка версии не нужна. `takeScreenshot()` (API 30), `takeScreenshotOfWindow()` (API 34)
и `canTakeScreenshot` в v1 **не используются**: глобальное действие отдаёт снимок системе,
приложение не сохраняет bitmap. Работоспособность на HyperOS проверяется в M2.8; до
проверки поддержку не обещать.

**«Голый Ctrl».** Проверяется в M2.6, сразу после первого рабочего маппинга: в M2.4
маппингов ещё нет, поглощать нечего. Чек-лист — `ARCHITECTURE.md` §16.2 (п. 15 и
чек-лист ниже). Побочный эффект обнаружен → остановиться и предложить отдельный ADR;
D-005 автоматически не менять.

**Фоновая доставка.** В фоне колбэки приходят пачкой, у отложенных событий
`descriptor=null` (`PROJECT_STATUS.md` §2 п. 13). Проверка — M2.8, п. 16 чек-листа; до
результата это открытый риск, а не гарантия.

**Клавиатура.** Физической клавиатуры нет: пункты с ней — SKIP до появления железа.

## M3 — Привязка профилей к приложениям (после v1)

**Цель:** автоматически выбирать профиль по foreground-приложению. Именованные профили,
CRUD и ручное переключение уже сделаны в M2; здесь добавляется только автоматика.

### Работы

1. `appBindings` + foreground-пакет из `TYPE_WINDOW_STATE_CHANGED`.
2. Разрешение профиля (привязка → активный → default → pass).
3. UI привязок: выбор из недавних foreground-пакетов или ручной ввод, без
   `QUERY_ALL_PACKAGES`.
4. Копирование профиля (опционально).
5. Тесты разрешения профиля.

### Критерии приёмки

- [ ] Привязка пакета: при переходе в приложение действует его профиль.
- [ ] Без привязки — активный профиль; без активного — default.
- [ ] Ошибка в привязке не ломает перехват (fallback).
- [ ] Unit-тесты на приоритеты.
- [ ] Ручное переключение по-прежнему работает и перекрывает привязку? (решить в M3:
      приоритет привязки или ручного выбора — зафиксировать в ADR).

**Оценка:** 1–2 сессии.

## M4 — Безопасность, диагностика, полировка

**Цель:** приложением можно пользоваться ежедневно и не бояться «залипшего» перехвата.

### Работы

1. Проверить crash-safe поведение D-006: падение, kill системой, перезапуск службы,
   перезагрузка → `armed=false`. Отдельный crash-guard не нужен.
2. Panic: Quick Settings tile (опционально, по ответу пользователя) + уведомление о
   включённом перехвате (если решим).
3. Экран Diagnostics: `appliedFlags`, история `deviceId`, фильтры, «сбросить журнал».
4. Обработка всех fail-safe сценариев D-018/§14 + тесты: повреждённый DataStore, ошибка
   записи, потеря мыши между DOWN и UP, сбой `performGlobalAction`.
5. R8/release: проверить, что служба, JSON и Compose не сломались; включить minify.
6. Полировка UI: пустые состояния, подтверждения, тексты, доступность.
7. Финальный ручной чек-лист на чистой установке.
8. Обновить `docs/PROJECT_STATUS.md` и `DECISIONS.md` по фактическим решениям.

### Критерии приёмки

- [ ] Падение/перезапуск не оставляет перехват включённым (D-006).
- [ ] `armed=false` после перезапуска службы и перезагрузки.
- [ ] Повреждённый/недоступный DataStore не блокирует ввод.
- [ ] Ошибка действия показывает сообщение и не роняет приложение.
- [ ] Release APK собирается и проходит чек-лист.
- [ ] Пользователь может выключить перехват за одно действие.
- [ ] Документация соответствует коду.

**Оценка:** 1–2 сессии.

## S3 (опционально) — «Вперёд» и инъекция

**Цель:** выяснить, можно ли получить браузерный «вперёд» и app-specific действия без
root, и стоит ли вводить Shizuku.

### Гипотезы для проверки

1. `performGlobalAction` не даёт «вперёд» — подтвердить перебором.
2. `GLOBAL_ACTION_DPAD_*` (API 31) не заменяет «вперёд» в браузере.
3. `dispatchGesture` (свайп) не даёт forward в Chrome/Edge.
4. Shizuku (`Shizuku.newProcess` + `input keyevent`) даёт `Alt+Right` / нужную комбинацию.
5. `INJECT_EVENTS` через Shizuku: какие ограничения на HyperOS 3.
6. Средняя кнопка через `onMotionEvent` + инъекция: сохраняется ли курсор.

### Результат

Короткий отчёт с таблицей «гипотеза → результат → цена». Решение о Shizuku — отдельно,
не автоматически.

**Оценка:** 1 сессия + живой тест.
