# WORKFLOW — OpenCode для Mouse Manager

Цель: минимум токенов на сессию при сохранении качества. Долговременная память — файлы,
кратковременная — контекст сессии. Всё, что должно пережить `/clear`, живёт в `docs/`.

---

## 1. Три уровня памяти

| Уровень | Где | Когда читается |
|---|---|---|
| Постоянный | `AGENTS.md` | автоматически в каждой сессии |
| Состояние | `docs/PROJECT_STATUS.md` | в начале каждой задачи |
| Решения | `docs/DECISIONS.md` | когда задача меняет поведение/архитектуру |
| План | `docs/ROADMAP.md` | при выборе следующей вехи |
| Код | `app/`, `spikes/` | точечно, по конкретным файлам |

Правило: **если факт важен, он должен быть в `docs/`, а не в истории чата.**

---

## 2. Одна сессия = одна задача

Плохо:

> «Сделай ремап, профили, диагностику и почини сборку».

Хорошо:

> «M2, шаг 3: реализуй `ChordTracker` и `RemapEngine` по `docs/ARCHITECTURE.md` §6.
> Файлы: `core/ChordTracker.kt`, `core/RemapEngine.kt`, `core/Verdict.kt`.
> Приёмка: unit-тесты из §16.1 проходят. Ничего не устанавливать.»

Сессия заканчивается, когда задача принята. Следующая задача — новый контекст.

---

## 3. Когда `/clear`

- Началась новая задача (даже если тема «та же»).
- Контекст перевалил за ~50%.
- Агент начал путаться в файлах или повторять уже отменённые решения.
- Переключение между вехами (M1 → M2).

После `/clear`:

1. Прочитать `AGENTS.md` (автоматически).
2. Прочитать `docs/PROJECT_STATUS.md`.
3. При необходимости — конкретный раздел `docs/ARCHITECTURE.md` / `DECISIONS.md`.
4. Не читать спайки и не пересобирать проект «на всякий случай».

---

## 4. Когда `/compact`

- **Только между задачами**, не в середине реализации.
- Когда жалко терять удачные формулировки, но контекст уже большой.
- После компакта **перечитать** `AGENTS.md` + `docs/PROJECT_STATUS.md`: это и есть
  восстановление памяти. Остальное восстанавливать не нужно.

Не делать `/compact` посреди отладки: потеряются точные значения (`flags=0x20`,
`descriptor`, номера строк), и придётся собирать их заново.

---

## 5. Шаблон запроса

```text
Веха: M2, шаг 3.
Цель: <одно предложение>.
Файлы: <точные пути>.
Ограничения: <что нельзя трогать>.
Приёмка: <проверяемый критерий>.
Не делать: <сборка/установка/спайки, если не нужно>.
```

Чем точнее файлы и критерий, тем меньше агент исследует и тем меньше токенов тратит.

---

## 6. Экономия на исследовании

- Указывать конкретные файлы, а не «разберись в проекте».
- Для поиска — `grep`/`glob`, а не чтение всего дерева.
- Читать файл целиком только если он небольшой; иначе — нужный диапазон.
- Не читать `spikes/`, если задача не про них: это архив доказательств.
- Не открывать `build/`, `.gradle/`, `*.apk`.
- Не запускать полную сборку перед каждым изменением: сначала правка, потом сборка.
- Для разведки использовать субагента `explore`: он вернёт выжимку, не засоряя основной
  контекст.

---

## 7. Экономия на логах и скриншотах

- Логи — фильтровать: `logcat -d -s MouseManager:D | Select-Object -Last 20`.
- Не вставлять в чат полный `logcat`; только строки, относящиеся к делу.
- Скриншот — только когда без него нельзя (визуальная проверка UI).
- Результаты сборки — только ошибки; успешная сборка = одна строка.

---

## 8. Git как память

- Commit после каждой принятой вехи.
- В задачах ссылаться на `git diff` / `git log --oneline`, а не пересказывать изменения.
- Перед реорганизацией — commit (страховка).
- Сообщения commit'ов: `M1: skeleton`, `M2: chord tracker`, `M2: remap engine`.

Агент может посмотреть `git diff` вместо повторного чтения всех файлов.

---

## 9. Типовой цикл вехи

```
1. /clear
2. Прочитать PROJECT_STATUS + нужный раздел ROADMAP
3. Задача = один шаг вехи
4. Правки → сборка → unit-тесты
5. Ручной чек-лист на устройстве (если нужен)
6. Обновить PROJECT_STATUS (и DECISIONS, если было решение)
7. Commit
8. /clear перед следующей задачей
```

---

## 10. Антипаттерны

| Антипаттерн | Почему дорого |
|---|---|
| «Посмотри весь проект и предложи улучшения» | Агент читает всё дерево |
| «Собери и установи, проверь» без конкретики | Полный цикл сборки + логи + скриншоты |
| Тащить обсуждение архитектуры в сессию реализации | Контекст занят историей, а не кодом |
| `/compact` в середине отладки | Теряются точные значения |
| Хранить решения только в чате | После `/clear` их нет |
| Читать спайки «для контекста» | Десятки файлов, польза нулевая |
| Возвращаться к отменённым вариантам | Тратятся токены на повторный анализ |

---

## 11. Ориентиры по бюджету

| Задача | Ожидаемый контекст |
|---|---|
| Мелкая правка (1–2 файла) | 10–20% |
| Шаг вехи (3–5 файлов + тесты) | 30–50% |
| Разведка + план | 30–40%, затем `/clear` |
| Отладка на устройстве | 40–60%, лог фильтровать |

Если контекст выше 60% — заканчивать задачу, обновлять `PROJECT_STATUS`, `/clear`.

---

## 12. Что делать после компакта

1. `AGENTS.md` — автоматически.
2. `docs/PROJECT_STATUS.md` — состояние.
3. `docs/ROADMAP.md` — текущая веха.
4. Конкретный файл, с которым работаем.
5. Всё остальное — по мере необходимости, точечно.

---

## 13. Роли документов

| Документ | Не должен содержать |
|---|---|
| `AGENTS.md` | длинную историю, детали реализации |
| `PROJECT_STATUS.md` | планы на будущее (только «следующий шаг») |
| `ARCHITECTURE.md` | даты, журнал изменений |
| `DECISIONS.md` | инструкции «как писать код» |
| `ROADMAP.md` | текущее состояние (только этапы) |

Дублирование между документами — главный источник рассинхронизации и лишних токенов.
